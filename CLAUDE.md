# StreamAssist — context for Claude

@README.md

## Purpose (in my words)

An "everything app" for streamers: playing music and sounds, notifications, chat commands, keybinds, etc. It has its own logic for configuring and triggering binds, and it also connects to existing software (Spotify, Voicemeeter, OBS, Twitch) for problems those already solve. It glues those tools together rather than replacing them.

Current state: the keybind component is partially done. Voicemeeter integration is basic: it mutes my mic going to OBS, or going to games/Discord, so I can talk to chat without bothering anyone else, or talk to Discord without chat hearing.

## Folder layout

- `Program.cs`, `App.axaml`, `ViewLocator.cs`: app entry point. `StreamAssist.Tests/`: the engine tests (see Tests below). `App.axaml` lists every shared resource and style file, in order.
- `Shell/`: the app window itself, meaning the main window, the resizable side/bottom/console panels, and `GlobalContext`. `MainWindowViewModel` is where models and managers get created. `WindowLayoutModel` (saved to `Config/window.json` by `WindowLayoutSaveManager`) remembers window position/size, maximized/fullscreen, the selected tab (Keyboard, Chatbot, Events, Connections), and every splitter, stored by name under `panelSizes`. A new resizable panel calls `GetPanelSize`/`SetPanelSize` with its own key. The window and panels also listen to the model's events, so code (e.g. a future action through `GlobalContext.WindowLayoutModel`) can change the layout.
- `Components/<Name>/`: one folder per feature (Keyboard, Blocks, Audio, OutputConsole, Chatbot, OBS, …), split into Model/Background/UI as described below. Code that belongs to a single feature lives in its component. `Blocks/` holds the block system: `Model/` (base classes, slots, `BindableModel`), `Containers/`, `Conditions/` and `Actions/` (the block classes), and `UI/` (editor, block list, and `Configurator/` for auto-generated block settings).
- `Core/`: reusable building blocks that know nothing about any feature. `Mvvm/` has the base classes and `ViewModelTabItem`, `Dragging/` the drag-and-drop helpers, `Connections/` the shared `ConnectionStatus` (Not connected / Connecting / Connected / Failed), `Persistence/` `JsonFileStore` and `CredentialStore` (every secret in one git-ignored `Config/auth.json`, one section per service: `twitchApps`, `twitchLogins`, later e.g. `spotify`; new integrations store credentials/tokens there, never in their own config file), and `Utilities/` small helpers (`GrowingList<T>`: a list that always ends in one empty item, used by Match Text rows, redeem rows and Join's parts, so the add/remove-empty-rows rules live in one place). `Mvvm/Flash` lights a view model flag up briefly (blocks and bind boxes flashing when they run). If something references a component, it doesn't belong in Core.
- `Styles/Resources/`: named values (`Brushes`: palette + meaning-based brushes, `Typography`: font + sizes, `Spacing`: shared margins like `HeaderMargin` and `PanelGapRight`). Views use them with `{StaticResource Name}`, and style files use `{DynamicResource Name}`.
- `Styles/Controls/`: one file per control type with app-wide styles and style classes (e.g. `Border.Draggable`, `Button.Square`, `ListBox.TopTabStrip`, `Button.Tab` for a panel's small tab bar with `.Open` on the open tab).

## XAML conventions

- ViewModel → View mapping goes through `ViewLocator`, so don't add a `DataTemplate` that only wraps the matching view. Only write an `ItemTemplate` when it adds something (extra elements, a different view).
- Repeated spacing goes in `Styles/Resources/Spacing.axaml` and colors in `Brushes.axaml`. Don't hard-code hex colors in views.
- **Spacing rule (keep it exact, it's very visible):** lines (dividers, splitters) run edge to edge across their panel, 5px from the next line or the window edge, and content sits another 5px inside (10px from a splitter to content). So:
  - Splitters carry their own gaps: the splitter column/row is `{StaticResource SplitterLength}` (15) and the `GridSplitter` gets `ColumnSplitterMargin` / `RowSplitterMargin`. The panels on either side get no gap margin, so a hidden panel (splitter length 0) leaves no gap behind.
  - Inside a panel, wrap the content (not the dividers) in `Margin="{StaticResource ContentInset}"`. A divider between sections is a sibling of the inset sections, never inside one.
  - Scrollbars count as lines: a panel's ScrollViewer gets `Classes="Gapped"` (`Styles/Controls/ScrollViewer.axaml`: the content stops 5px before the bars instead of running under them) and no margin of its own, so its bars reach the panel's edges. Its content carries the inset instead (e.g. `Margin="5,5,10,0"` on a scrolled block tree, `Padding` on text that has to fill the viewport). Don't add `Gapped` to scroll viewers inside other controls (text boxes, combo boxes, tab strips). Leave the bars thin (the default, no `AllowAutoHide="False"`): they stay on screen as a thin line and widen when hovered, and `Gapped` spaces the content from the thin line.
  - A tab's main scroll area (and the bottom editor) ends with extra room to scroll the last row up: wrap its content in `<Border Padding="{StaticResource ScrollEndPadding}">` (200px, change it in `Spacing.axaml`). A ScrollViewer's own `Padding` doesn't add scroll room.
  - Header rows above a divider use `HeaderMargin` and `Height="{StaticResource HeaderHeight}"` (a search box as a header also gets `MinHeight="0"`, like the block list's) (tab strips get it from their style), so side-by-side headers' dividers line up. A divider under a header uses `DividerMargin`.
  - Check new layouts against the existing ones (the tab bar divider and the Output divider are the reference).
- Styles needed by only one view go in that view's `<UserControl.Styles>` (e.g. a view-specific `<UserControl.Styles>` block). App-wide ones go in `Styles/Controls/`.
- Style class names are case-sensitive (`Label`, not `label`).
- `Border` has no global style. Add `Classes="Panel"` for the rounded panel look (keys, action cards, drop zones). `Divider` is a separate class.
- Button sizes: `Small` (corner buttons on keys/actions), `Medium` (next to inputs), `Large` (standalone). Combine with `Square` for icon buttons, e.g. `Classes="Square Medium"`. Plus/minus icons use the full-width `＋` / `－`.

## Architecture rules

Each component (`Components/<Name>/`) is split into three folders:

- **Model/**: data only, always loaded, serialized to JSON. Models are the "shouters": they raise C# events when they change. They never execute behavior.
- **Background/**: managers created once at startup that live for the whole app (`KeyboardComponentManager`, `KeybindManager`, `KeyboardSaveManager`, `VoicemeeterManager`). They listen to models and do the actual work (dispatching key presses, saving).
- **UI/**: view models + views. A view model is created when its tab or panel opens and disposed when it closes. View models listen to models, and change things only by calling model methods, never by calling managers. Model events then update the background and any other UI.

So data flows: UI → model method → model event → (background + UI listeners). Something with no UI (chat command, timer) can drive the model the same way.

**Everything the UI can do must be a public model method** (bind/unbind a key, remove a block, disable something, switch config, add a slot, …), with the rules enforced inside the model, not in view models. The goal is that a block, chat command or any other code can do anything the user can, just by calling the same model methods, and the UI updates because it listens to the model.

`MainWindowViewModel` is the composition root: it loads models, creates managers, and sets `GlobalContext` (a static service locator that actions use to reach managers like `VoicemeeterManager`).

## Code conventions

- Public `TryXxx(...)` methods validate, log through `AppLog.WriteError`, and return `bool`. They call a private `Xxx(...)` that does the work and raises the event.
- Every event subscription goes through paired `SubscribeToXxx` / `UnsubscribeFromXxx` helpers. `Dispose()` must unsubscribe everything.
- JSON: public getters are `[JsonIgnore]`. Serialization goes through private `[JsonInclude] [JsonPropertyName("camelCase")]` properties. Links that need the whole tree (e.g. slot → config by name) are resolved in `IJsonOnDeserialized.OnDeserialized` or `AttachXxx` methods.
- A child gets a callback to remove itself from its parent through `AttachUnbindSelf(...)` (e.g. an empty action group unbinds its trigger, and an empty keybind unbinds its key).
- `CallbackBlocker` stops UI → model → UI feedback loops when a view model sets its own bound properties.
- Views are found by naming convention (`ViewLocator`): `FooViewModel` → `FooView` in the same namespace.
- Style: `_camelCase` private fields initialized explicitly in the constructor, `// section` comment headers, three blank lines between members.

## Blocks and bindables

Everything that triggers (keys now, chat commands/timers later) owns a `BindableModel` with one root `BlockSlot`. Blocks nest Scratch-style. All of this lives in `Components/Blocks/`.

- Triggers: `TriggerStart()` (key down), `TriggerStop()` (key up), and `TriggerOnce()` (instant things like chat commands). Each one runs the root block once with a `TriggerContext` (`Phase` = Start/Stop/Once, plus a `CancellationToken`). OS key repeat is ignored.
- Running: the root runs through `SafeRunAsync` (catches errors). Blocks call children with `slot.RunAsync(context)` / `list.RunAllAsync(context)`, which don't catch. An error stops the rest of the tree.
- **Errors are logged where they happen:** a block that can't go on does `throw Fail("reason")`, which logs `Could not run '<block>' - <reason>` (a value slot's `Fail` adds the slot label, e.g. `Could not run 'Round' - Number: 'abc' is not a number`) and throws `BlockFailedException`. That stops the run, and `SafeRunAsync` doesn't log it again. Only unexpected exceptions are logged by the root. `RunAsync` checks the block's own `IsDisabled` and returns early, so a disabled block skips everything inside it, but only the disabled block shows red.
- Execution is truly async: `ExecuteAsync` returns a Task, and plain `await` comes back on the UI thread. Pass `context.CancellationToken` to anything that waits. Disposing a bindable (key unbound, app closed) cancels its running trees.
- Block kinds (base class → block list heading): `ContainerBlock` (has slots, e.g. List, If, On Pressed, On Released), `ActionBlock` (does one thing, e.g. Play Sound), and value blocks (`ValueBlock<T>`, `ComputeAsync` returns a value, listed under the type they return: Bool, Text, Int, Double, Char). `ConditionBlock` is the bool value block (`CheckAsync`, a disabled or empty condition counts as false).
- **Values** (`Blocks/Model/ValueKind.cs`, `ValueBlock.cs`, `ValueSlot.cs`, blocks in `Blocks/Values/` and `Blocks/Conditions/`): the kinds are text (string), int, double, bool and char. A block's setting that can come from logic is a `ValueSlot<T>`: a text box (its placeholder says what fits, e.g. `+ int`) or a value block placed in it (the block wins, a disabled block falls back to the typed text). Typed text has `{name}` parameters filled in first and is then read as the slot's kind, so an int slot can be `{viewers}`. `ValueTypes` is the one place that decides conversions: a slot accepts its own kind plus automatic conversions (int → double, anything → text, numbers written with `.`), everything else goes through the **Convert** block (`ValueTypes.TryConvert`: text into anything, failing with an error if it doesn't fit; double → int truncates). Round stays as a separate math block (Round / Floor / Ceiling / Truncate). **Operation** (`OperationBlock`, any-type) has an Op dropdown (+ − × ÷) and a growing list of number slots (no labels), worked through top to bottom (`10 − 3 − 2 = 5`, + and × over any number of numbers, so no nesting). It has no type dropdown: like C#, if every number is whole the maths is whole (`7 ÷ 2 = 3`) and a decimal anywhere makes the answer a decimal; what it gives (Int or Double) follows the slot it's dropped in (decimal by default, saved as `kind`), and in a whole number slot a decimal answer drops its decimals. Dividing by zero fails. **Expression** (`ExpressionBlock`, any-type the same way) works out a typed formula: one text slot, `{name}` parameters filled in first, then `Core/Utilities/Formula` reads numbers, `+ - * / %` (and `× ÷ −`), parentheses and signs, typed like C# per part of the formula (whole numbers stay whole, `7/2 = 3`; a decimal makes that part decimal, `7/2.0 = 3.5`). A formula it can't read fails naming it (`Could not run 'Expression' - '25/0' - can't divide by zero`). Use Expression for typed maths and Operation when the numbers come from other blocks. **Join** puts a growing list of text parts together top to bottom (like `$"..."`): a `ValueSlotList` of text value slots with one empty part always at the bottom (typing in it or placing a block adds the next, a part with no text and no block disappears, like Match Text rows). `ValueSlotList(label, kind)` holds value slots of any one kind (Operation's are decimal), `EvaluateFilledAsync<T>` reads every filled one.
- **Any-type blocks** (`AdaptableValueBlock`, listed under "Any type"): Convert ("To") and Get Parameter ("As") return whichever kind their dropdown says. Every slot has a `WantedKind` (Bool for condition slots, the slot's kind for value slots); dropped into a slot, an any-type block switches to it if it doesn't already fit (a saved one keeps its kind). Each block knows its `ParentSlot`, and changing the dropdown to a kind that slot can't take is refused with a console error. Condition slots (If, And, Or, Not, Xor) take any bool value block, evaluated with `ConditionBlock.EvaluateConditionAsync`. `AnyValueSlot` takes any kind (Equals): typed text takes the kind of the block on the other side, different kinds are never equal except int and double (`5 == 5.0`). Parameters are always text, Get Parameter reads them as its "As" kind (and says which parameter didn't fit).
- **Parameter lists:** what each trigger passes is data (`ParameterInfo`: name, kind, description). The chatbot's are in `ChatEvents` (`Chat`, `Rest`, `Redeem`, `Parameters(eventKey)`, `Common`), and `ChatbotComponentModel.FindParameters(target)` gives a bind box's list (a chat command adds what its path captures: Parameter block names and regex `(?<name>...)` groups). The editor shows it under a collapsible **Parameters ▸** in its header (`ShowBindable(..., parameters)`, keys have none so no button). The engine tests check the lists match what twitch events and the test panels really give, so add a parameter in both places. Variables (later, maybe a database) would just be more value blocks.
- Slots are typed: `new BlockSlot(label, typeof(ExecutableBlock))` for blocks that run, `typeof(ConditionBlock)` for conditions, `new ValueSlot<T>(label)` for values. A slot's `Filter` narrows what it takes beyond the type (value slots use it for conversions), its `Lock` refuses blocks for a while, and its `Owner` (set by `TrackSlots`) is the block it belongs to. `BlockSlotList` is the expanding version. `BlockBranchList` (used by `IfBlock`) is a list of `BlockBranch` (condition slot + then slot). Dropping a condition on a branch creates a new branch before it (the zone at the end adds one last), and a branch removes itself once both its slots are empty, so a filled "then" is never lost. Lists work the same way: one drop zone at the end, and dropping on an item puts the new block before it (a line above it lights up, `Border.InsertBefore`), so reordering is dragging a block onto the one it should go before. The drop target nearest the pointer handles a drag (`DropBehaviorHandler` marks it handled), so nested targets never both take a drop.
- Slot labels (an if's "if" / "else if" / "else", the then slot has none) sit beside their slots in a fixed-width column (`SlotLabelWidth`), so every row's slot lines up. A block whose `SlotsBesideSettings` is true shows its slots to the right of its settings instead of under them (Parse Parameter: name, then the block slot and bind box).
- Drop targets: every slot's empty `+` zone is the shared `Blocks/UI/DropZone` control (`IsCondition` picks the block or condition look). Change the drop zone shape/text there only, never inline in slot views.
- Each slot kind has a matching view model/view in `Blocks/UI` (`BlockSlot*`, `BlockSlotList*`, `BlockBranchList*`), picked in `BlockViewModel`'s constructor. A new slot kind needs one there too. Slots that hold other slots (like branches) expose them through `InnerSlots`, so the "can't drop a block into itself" check sees them.
- Change tracking bubbles up: any parameter, disabled state, or slot change raises `Changed` on the block, then its parent, up to `BindableModel.Changed`. Saving only listens there.
- Empty bindables remove themselves: when a bindable's root block is removed (from the UI, `Clear()`, or any other code), it calls the unbind callback its owner attached (`AttachUnbindSelf`, set by `KeybindConfigModel`), so no `"root": null` bindings are saved. This only happens when the root block is removed, not on save. Empty bindables in an old save file are dropped once on load.
- Key input: `KeyboardInputManager` keeps the set of held keys per keyboard (`IsKeyDown(vk)` / `IsKeyDown(device, vk)`, reachable through `GlobalContext.KeyboardInputManager`). It updates the set before raising `KeyDown`/`KeyUp`, and `KeyDown` only fires on the first press (no OS repeat). Left/right Shift/Ctrl/Alt share a code. Keys can get stuck as held if Windows swallows a key-up (e.g. Win+L), not handled yet.
- `KeybindManager` caches nothing: on each key event it walks the slots, matches the device, and looks the key up in the slot's selected config, so model changes apply immediately. Start/Stop aren't paired (a release goes to whatever is bound at release time), which is intentional.
- Typing key names: `DeviceDisplayHelper.TryParseKeyName` accepts aliases (`ctrl`, `esc`), windows names (`SHIFT`, `F5`, `NUMPAD1`, `DIVIDE`) and characters on the keys (`;`, `/`, which mean the main-row key, not the numpad one).
- **Shared bottom panel editor:** `Blocks/UI/BindableEditorViewModel` + `BindableEditorView` (bindable's block tree + Containers/Conditions/Actions list + splitter). Any tab that edits bindables puts one in the bottom panel and calls `ShowBindable(bindable, label, parameters)` for a saved binding, `ShowDraft(label, save, parameters, startWithOnPressed)` for something with no binding yet (an unsaved draft: keys start with an On Pressed, chatbot bind boxes start empty since they just fire once; `save` binds it on its first change that leaves it with a block, and an unchanged draft is thrown away), or `ClearBindable()`. `KeybindViewModel` derives from it and adds key selection; the chatbot tabs use it directly for bind boxes.
- **EditButtons** (`Blocks/UI/EditButtons.axaml`, shared by blocks, keys and bind boxes) are in the order collapse, enable/disable, move, remove. Keys and bind boxes show them while the pointer is on one that has a binding (`EditButtons.HoverOnly` + a `Border.Bound:pointerover` style in the view), whether or not it's selected. A block card shows them only while the pointer is on that card itself, not a block nested inside it (`BlockView` keeps one hovered card, listening to handled pointer moves too since text boxes and dropdowns handle them). They're hidden by opacity so the title row keeps its size.
- **Collapsing:** every block has `IsCollapsed` (saved with it, `SetIsCollapsed`). The `▴` corner button collapses a block to a drop-zone-sized box that keeps its outline and shows `▾`, and clicking that box expands it. Keys don't collapse (`IEditButtons.CanCollapse`).
- Keys: a key is green when its root slot has a block. Selecting an unbound key shows an unsaved draft with an empty On Pressed, which gets bound to the config on its first change. 
- Binding slots vs block slots: a **binding slot** (each key, later chat commands, …) holds a whole `BindableModel`, and **block slots** live inside a bindable's tree. Blocks are only placed in the editor, never dropped on a key. Whole bindings move between binding slots with `BindableDragPayload` (drag a selected key's handle onto another key). A binding slot only accepts a drop when it's empty, and the source is removed only after the copy is bound.

## Adding a block

Create a class in `Components/Blocks/Actions/`, `Containers/`, `Conditions/` or `Values/` that inherits `ActionBlock`, `ContainerBlock`, `ConditionBlock` or `ValueBlock<T>`, and implement `Name`, `Description` and `ExecuteAsync` (or `CheckAsync` / `ComputeAsync`). `BlockResolver` finds it automatically, and it appears in the block list under its category (value blocks under the type they return). When it can't go on, `throw Fail("reason")`.
- Settings a user might want to come from logic (text, numbers, true/false) are `ValueSlot<T>`s: create them in the constructor like any slot, read them with `await slot.EvaluateAsync(context)`, and save them through a private `[JsonInclude]` property using `GetData()` / `LoadData(value)` (see `ConsoleMessageAction`, `CompareCondition`).
- Fixed settings (a menu choice, a file path, a parameter name) are properties marked `[ConfigurableParameter("Label", ConfiguratorType.X)]` whose setter calls `SetParameter(ref _field, value)`.
- A `Menu` parameter gets its options from a `public static List<string> Get{PropertyName}MenuItems()` method. A `Slider` gets its range from `public static (double, double) Get{PropertyName}Bounds()`.
- Containers: create slots in the constructor, return them from `Slots`, call `TrackSlots()` at the end of the constructor, and save each slot through a private `[JsonInclude]` property using `slot.GetData()` / `slot.LoadData(value)` (see `OnPressedBlock`, `ListBlock`). The editor UI is generated from `Slots`, so no new view is needed.
- Mark `Name`, `Description` and `Slots` overrides `[JsonIgnore]`.
- **The class name is the JSON key.** Renaming a block class drops saved blocks of that type.

## Chatbot

`Components/Chatbot/` follows the same Model / Background / UI split.
- **Model:** `ChatbotComponentModel` holds the one Client ID/Secret both accounts log in through (`SetCredentials`), each account's saved `ConnectOnStartup` / `BotConnectOnStartup`, their session-only `IsEnabled` / `IsBotEnabled` (they start as the startup setting and aren't saved), and the two chat block trees: `Root` (protected, a fresh chatbot gets an empty Match Text there; saved as `rootBlock`) and `EditableRoot` (chat-editable, saved as `editableRootBlock`, see Two roots below). The tree and startup settings are saved to `Config/chatbot.json`, the credentials to the `twitchApp` section of `Config/auth.json` (both git-ignored). Connecting/disconnecting is `SetIsEnabled` / `SetIsBotEnabled`, and retrying is `Reconnect` / `ReconnectBot` (also connects if it was off). Anything can call them.
- **Two accounts:** the **streamer** login listens (EventSub only sends redeems/subs/bits/follows to the broadcaster, and one websocket carries one account's subscriptions). The optional **bot** login is only used to send chat. Without a bot, chat is sent as the streamer. Each account's tokens remember which app made them. Both are in the Connections tab. Connect uses the saved login, or the first time shows a login link in the console (the bot's has to be opened in a private browser window logged in as the bot). Disconnect keeps the saved login and the Client ID/Secret. Tokens for both are in the `twitchLogins` section of `Config/auth.json`. The app is a Confidential Twitch app, so the device code flow sends the client secret.
- **Chat blocks** (`Chatbot/Blocks/`) are `BlockModel`s in the `Chat` category. **Match Text** is a list of rows (`MatchTextRowList` of `MatchTextRow`): each row is a pattern plus a `ChatTarget` to its right. A pattern is **plain text** by default, or a **`/regex/`** in slashes (`ChatText.TryGetRegex`, `MatchTextRow.TryMatchAt`). Plain text is matched literally, case ignored, spaces at the ends trimmed, and as whole words: one ending in a letter/digit can't be followed by one (`lurk` matches `lurk`, `lurk ahaa`, `lurk!`, never `lurker`). Spaces only matter between words (`ChatText.SkipGap`): after a word the spaces before the next piece are skipped (`pay` then `all` matches `pay all`, not `payall`), after a symbol nothing is skipped (`!` then `lurk` matches `!lurk`, not `! lurk`). A `/regex/` is matched exactly as written where the previous piece stopped (`\G`), case-insensitive unless it says `(?-i)`, named groups `(?<name>...)` become parameters. `//` is the empty regex: it matches nothing, so always (e.g. a last row for anything else, with the unmatched text in `rest`). There's always exactly one empty row at the end (typing in it adds the next). A row disappears when its text is empty and its target is empty, and a row with no text is skipped when matching. **Parse Parameter** (`ParameterChatBlock`, the class keeps its old name for saves) has a name, a **Reads** dropdown (Next word / Rest of message, no regex) and one `ChatTarget`. It follows the same spacing rule as plain rows: after a word it skips the spaces (and won't start in the middle of a word, `!sofoo` doesn't give `!so` a parameter), after a symbol it reads right away (`!` then a parameter reads `!lurk` as `lurk`). The rest of the message is trimmed (it can be empty). After Rest of message nothing is left to match, so its target `EndsHere` (`ChatTarget.SetEndsHere`): the child slot's `Lock` refuses blocks and the `+` slot hides (a block already there stays visible). The bind box text joins steps the same way (`ChatText.Join`: a space where two words meet, a `{name}` counting as a word, e.g. `!pay all`, `!addcom {command} {content}`, `!{cmd}`; a regex shows as written, `//` adds nothing). Slot kinds from other components are shown through `BlockViewModel.RegisterSlotViewModel` (the chatbot registers `MatchTextRowListViewModel` and `ChatTargetViewModel`).
- **Has Permission** (`HasPermissionChatBlock`) lets only some chatters past it: an "At Least" dropdown (Subscriber < VIP < Moderator < Broadcaster, each level includes the ones above it) plus a `ChatTarget`. Anyone else (or a run with no chatter) falls through to the next row. It matches no text and adds no step to the command path.
- **Two roots:** `Root` (shown as "Protected") and `EditableRoot` ("Editable"). Messages try the protected tree first, then the editable one (`ChatbotComponentModel.TryMatchMessage`), so chat can't override a protected command. The editable root only takes a **Match Text** (a fresh or older config gets an empty one), and that tree holds the editable commands. `TryAddCommand` / `TryEditCommand` / `TryDeleteCommand` find a command by walking down plain text rows like matching does (`FindCommand`: `!lurk` goes through a `!` row into the Match Text after it, then its `lurk` row), and only touch a whole command: a plain text row completing the command (case ignored) that runs a binding. `/regex/` rows (including `//`) are never commands and never walked into, and a row leading into more blocks (e.g. `!`) isn't a command. A command written in slashes is refused (it would read as a regex). Add puts the new row in the first Match Text the walk reaches that has nothing more for it (under the `!` row if there is one, else at the top), as the rest of the command in plain text (`hello`), which matches whole words, so `!hi` doesn't run for `!hiya`. Add binds a lone Send Chat Message, and edit only works on a binding that is just that (anything more is edited in the app). Each method can also give a `CommandFailure` (NotFound, AlreadyExists, NotSimple, Invalid). The Add/Edit/Delete Command action blocks pass `logErrors: false` when a chat message started the run (`ChatEvents.IsFromChat`) and reply in chat instead (`CommandActionHelper`: "command not found", "command already exists", "could not edit command", no reply for Invalid). Run from anything else, the model logs `Could not edit command '!x' - it doesn't exist` etc. Either way a failure stops the binding, so a reply after them only goes out on success.
- **ChatTarget** (`Chatbot/Model/ChatTarget.cs`) is what happens after a row/Parameter matches: **either** a binding (`BindableModel`, run with `rest` = the unmatched remainder) **or** a child chat block slot to keep matching, never both. The model enforces it: `TryBind` fails if the child slot is filled, and the child slot's `Lock` refuses blocks while bound (`BlockSlotBase.Lock` is a general "refuse blocks right now, here's why" hook). A binding whose blocks are all removed unbinds itself, like a key. On **load only**, a saved target with both keeps the binding, drops the block and logs a warning (nothing is checked on save). JSON: a row saves `pattern`/`bindable`/`child`, a Parameter saves `target: {bindable, child}`.
- **Bind box** (`ChatTargetView`): the box after the row's `+` slot, which works like a key. It shows the command that reaches it, like a key shows its name: every row (plain text, or a `/regex/` as written) and Parameter (`{name}`, `{?}` if unnamed) on the way down, joined like matching reads them, e.g. `!pay {user} {amount}` (`ChatbotComponentModel.FindCommandSteps`/`FormatCommand`, also used for the editor header). Its text is left-aligned with a button-wide gap on the right (an invisible copy of EditButtons), so it stays put when the real buttons appear there. It is 25 tall, at least 100 wide and at most 300 (longer commands end in … and show in full as a tooltip). Grey text = an unbound preview, green = bound, red = disabled, purple flash when it runs (`BindableModel.Triggered`). Clicking it opens it in the bottom editor (an unbound one gets an unsaved On Pressed draft that binds on its first change, like keys), clicking again closes it, and hovering a bound one shows EditButtons inside the box (drag the binding to another bind box or a key, disable, remove). The bind box hides once a block fills the `+` slot, and the `+` slot hides once it's bound. Which box is open is `ChatTargetSelection` (static, since the boxes are built deep in the block tree).
- **Matching** (`model.TryMatchMessage(...)`, run by `ChatCommandManager` for every chat message: the protected root, then the editable one): blocks/rows are tried top to bottom, each one reading on from where the previous one stopped (see plain text vs `/regex/` above). Something that matches but doesn't lead to a binding falls through to the next row. The **first** binding reached runs and the search stops. Disabled blocks and disabled bindings are skipped. An invalid pattern is logged once and never matches, and patterns time out after 100ms. Messages from the bot account are ignored. Chat blocks flash purple (raise `Triggered`) when they **match**, even if nothing after them does: a Match Text when any of its rows' text matched, a Parameter when its pattern matched, a bind box when its binding runs. So `!bruh` lights up the block with the `!` row and nothing after it.
- **Parameters** travel with each run in `TriggerContext.Parameters`, never in `GlobalContext`. Each run gets its own copy (the `TriggerContext` constructor copies them), and **Set Parameter** (`Blocks/Actions/SetParameterAction`: a name of letters/digits/_ and a value slot) adds or replaces one for the rest of that run with `context.SetParameter`, stored as text (`ValueTypes.ToText`), so a value from any block (e.g. Get Reward Setting) can be used as `{name}` in text, formulas and typed values further on. Nothing is kept between runs, and the editor's Parameters ▸ list doesn't show set ones. Every chat trigger gets `user`, `userLogin`, `userId`, `message`, `messageId`, `channel`, `channelLogin`, `channelId`, `timestamp`, `color`, `badges`, `isBroadcaster`, `isModerator`, `isVip`, `isSubscriber` (`TwitchEvent.ChatParameters`), plus `rest` and anything the chat blocks capture. Text settings use them as `{name}` via `context.Format(text)` (Console Message, Send Chat Message).
- **Background:** `ChatbotManager` watches the model and connects while enabled. Every connection (Twitch, the bot, Voicemeeter) makes **one** attempt (at startup if connect on startup is ticked, or when Connect/Retry is pressed): a failure, or a Twitch connection dropping later, is logged to the console once and left as Failed, never retried automatically (Twitch moving the websocket to another server is still followed, that's part of staying connected). A connection that drops after it was working is a warning (`Could not stay connected to Twitch as the streamer - <reason>, press Retry in the Connections tab to reconnect`, status Disconnected), not "could not connect". **Logins stay fresh by themselves:** twitch tokens run out after a few hours, so `KeepLoginsFreshAsync` checks both logins every 30 minutes (`TwitchAuthManager.TryValidateAsync`, twitch wants apps to check about hourly) and refreshes one with under 45 minutes left (`TryRefreshAsync`, saved to auth.json); an action whose token is refused anyway refreshes once and retries (`TryRefreshSessionAsync`, one refresh at a time). Only twitch refusing the refresh token counts as the login being gone (`RefreshAsync` throws `TwitchUnauthorizedException` for 400/401/403, anything else is retried at the next check): then the login is forgotten, that account stops (`OnLoginLost`) and one warning says to press Retry (the bot's says chat goes out as the streamer until then). It uses `TwitchAuthManager` for logins and `TwitchEventSubClient` (EventSub over websocket, handling reconnect messages and keepalive timeouts), and subscribes to everything in its `Subscriptions` table. Adding an event type is one line there plus a constant/description in `TwitchEvent`. Subscriptions the account isn't allowed are logged and skipped. `EventReceived` / `StatusChanged` are raised on the UI thread. The status text beside each Log in button is a short state only, and failures go to the console (each failed attempt is logged once). **Twitch actions** (`TrySendChatMessageAsync`, `TryTimeOutUserAsync`, `TryBanUserAsync`, `TryDeleteChatMessageAsync`) are done as the bot if it's connected, otherwise as the streamer, and all take turns in one `TwitchActionQueue`: at most one per `ActionInterval` (1 second), in the order asked, so busy chat can't make the account spam twitch. They log their own failure (`Could not time out 'x' - ...`) and return false, the blocks (`Chatbot/Actions/`: Send Chat Message, Time Out User, Ban User, Delete Message) then stop the run with `BlockFailedException`. Usernames are login names (an @ is ignored), looked up when the action runs. Twitch won't post the same chat message twice in a row, so a message identical to the last one sent gets a space + U+034F (an invisible combining grapheme joiner) at the end (`AvoidDuplicate`), repeats alternate with and without it. Timeouts, bans and deletes need the account to be a moderator. **Channel point rewards** are always done as the streamer, never the bot (only the broadcaster can manage rewards, so only the streamer login asks for `channel:manage:redemptions`; the bot's scopes are just chat and moderation): `TryGetRewardSettingAsync`, `TrySetRewardSettingAsync`, `TryCreateRewardAsync` (same queue, `TryRunActionAsync(..., asStreamer: true)`), a reward found by its id or title. `RewardSettings` (`Chatbot/Model/RewardSettings.cs`) is the one table of settings the blocks offer (Cost, Title, Prompt, Enabled, Paused, Viewer types text, Skip request queue, Cooldown seconds, Max per stream, Max per viewer per stream, Background color): each one's kind and how it's read from / written to twitch's reward json (limits read 0 when off, writing 0 turns them off). **Twitch only lets the app that created a reward change it**, so Set Reward Setting fails on rewards made in the dashboard (the error says so); rewards are created through the New reward panel. Blocks: **Get Reward Setting** (`Chatbot/Values/`, any-type: picking a setting picks its type, a placed one converts), **Set Reward Setting** (`Chatbot/Actions/`, the value is converted to the setting's kind); both take the reward as `{reward}` (the title of the one just redeemed) by default, a typed title or id works too. The manager and model are in `GlobalContext`.
- `TwitchApi` is the only place that talks HTTP to Twitch (no Twitch library is used: logins, EventSub and Helix are done directly).
- **Redeems and stream events:** `ChatbotComponentModel.Redeems` (`RedeemList` of `RedeemRow`: an exact reward title, case and surrounding spaces ignored, no regex, plus a binding; same trailing-empty-row behaviour as Match Text) and `Events` (one `ChatEventSlot` per entry in `ChatEvents.All`: Follow, Sub, Gift Subs, Cheer, Raid, Stream Online, Stream Offline). Both use binding-only `ChatTarget`s (`allowsBlocks: false`). `ChatEventManager.Dispatch` turns each Twitch event into parameters and calls `Redeems.TryRun(title, ...)` / `TryRunEvent(key, ...)`. The parameter names for each event are listed in `ChatEvents.cs`. New subs and resubs both go to Sub (`months` = 1 for a new sub; resubs only arrive when the viewer shares their resub message). Gifted subs are skipped there so Gift Subs alerts once per gift. JSON: `redeems: [{title, bindable}]`, `events: {key: bindable}` (only bound events are saved, unknown keys are skipped with a warning on load). `Redeems.AddRow(title)` adds a row (or returns the existing one). Creating a reward: the New reward panel calls `ChatbotComponentModel.TryRequestCreateReward(title, cost, prompt, userInputRequired)`, which checks it (a title of at most 45 characters, a whole cost of at least 1) and raises `CreateRewardRequested`; `ChatbotManager` creates it on twitch and then adds its redeem row. `Describe(target)` names any bind box (`("Chat command", "!lurk")`, `("Redeem", "Hydrate")`, `("Alert", "Raid")`) for the box text and the editor header.
- **Chatbot and Events tabs:** two main tabs, both `ChatbotComponentViewModel` (`ActivateChatTab` / `ActivateEventsTab`), which owns the bottom panel's `BindableEditorViewModel` (the same editor the Keyboard tab uses) and the bind box selection, and hosts one page: `ChatCommandsViewModel` (the Protected and Editable trees with their own Chat Blocks list, and a Test panel that sends a made-up message with a user and Mod/VIP/Sub badges through the tree like a real one, `ChatEvents.SampleChatParameters`) or `ChatEventsViewModel` (one left-aligned column: Alerts, the event bind boxes, then Redeems; at the bottom a Test panel whose made-up User/Amount/Tier/Text values feed a Test button on every row through `ChatEvents.SampleParameters`, and a New reward panel). Both pages end in a small tab bar (`Button.Tab`): closed it's one line, a tab opens its panel underneath (fields stacked downwards, the list above gets shorter), the open tab closes it, and only one panel is open at a time. Clicking a bind box opens its binding in the editor (its header names it, e.g. `Chat command: !lurk`, `Redeem: Hydrate`, `Alert: Raid`). The slot view models (`MatchTextRowListViewModel`, `ChatTargetViewModel`) are registered per tab because bind boxes need the model. The window side panel is unused on these tabs, and the twitch logins are in the Connections tab.

## Connections

The **Connections** tab (`Components/Connections/UI`, no side or bottom panel) has one section per outside program: Twitch (Client ID/Secret, then Streamer and Bot rows), Voicemeeter, and OBS/Spotify placeholders. Every row is a `ConnectionRowViewModel`: a status box (green outline = connected, red = failed, grey otherwise, details in its tooltip), one button (Connect when not connected, Disconnect while connecting/connected, Retry after a failure) and a Connect on startup checkbox, then while connected which account it is in muted text (`ConnectedText`, e.g. "Connected as budderbot"). The row is given how to read and change its connection; it only calls model methods (`SetIsEnabled(false)`, `Reconnect()`, `Set...ConnectOnStartup`), and the managers react and report their `ConnectionStatus` (`ChatbotManager.StreamerConnection` / `BotConnection`, `VoicemeeterManager.Status`). Connect / Retry on a Twitch row first saves the Client ID/Secret boxes. A new integration = a model with a saved connect-on-startup setting + session-only enabled flag + reconnect method, a manager with a `Status` and `StatusChanged`, and a row in the tab.

- **Voicemeeter:** `AudioComponentModel` (`Config/audio.json`, saved by `AudioSaveManager`) holds `VoicemeeterConnectOnStartup` and the session-only `IsVoicemeeterEnabled`. `VoicemeeterManager` connects when the model says so (`VoicemeeterConnectionChanged`), including at startup.

## Tests

`StreamAssist.Tests/` is an xUnit project that checks the engine (models, blocks, matching, background managers) without opening a window. Run it with `dotnet test StreamAssist.Tests` (a bare `dotnet test` in the root only sees the app project, and a solution file next to it would break the bare `dotnet build`). It builds the app too, so close the running app first (it locks the exe).
- `EngineChecks.RunAsync` is one long list of `Check("what it checks", condition)` lines grouped in `// ---- section ----` blocks, run in order (later sections reuse helpers and some state from earlier ones). `EngineTests` runs it as a single xUnit test: every PASS/FAIL line goes to the test output, and the failure message lists the failed checks by name.
- When changing behaviour, add or update checks in the matching section. Test-only blocks (`RecordBlock`, `FixedCondition`, `ChatLogBlock`, `ParamRecordBlock`, `KeysRecordBlock`, `SwapConfigBlock`) record what ran.
- Checks that count console errors (`Errors()` / `LastError()`) must come before the first `await`: `AppLog` posts through Avalonia's dispatcher, and only the thread that first used it can run its queue (`Dispatcher.UIThread.RunJobs()`).
- The app project excludes this folder (`DefaultItemExcludes` in `StreamAssist.csproj`), so its files aren't compiled into the app.

## Threading

Right now everything runs on the UI thread, because raw key input arrives through a hooked window procedure (`KeyboardInputManager.WndProc`). Future integrations (Twitch, OBS websocket, Spotify) will call back on other threads. Switch back to the UI thread with `Dispatcher.UIThread.Post` before touching models.

## Environment and setup notes

- Windows only, .NET 10, Avalonia 12, CommunityToolkit.Mvvm. Build with `dotnet build`, test with `dotnet test StreamAssist.Tests`.

## Known issues (found in review, not fixed yet)

- `JsonFileStore.Load` ignores parse errors and returns defaults, and `KeyboardComponentManager` saves right away. A bad config file gets overwritten with an empty one.
- `KeyboardSaveManager.Dispose` cancels the pending save instead of saving immediately, so changes made in the last second before closing are lost.
- Remove slot with zero slots crashes (`KeyboardListViewModel` calls `Slots.Last()`).
- `KeyboardSlotModel.Dispose` disposes the selected config and device, which it doesn't own.
- Voicemeeter toggle uses a remembered mute state (it doesn't read the real one back), connecting resets mutes and gains, and `TrySetGainDb` stores the unclamped value.
- Device list skips devices with the same vendor/product ID, so identical keyboards collapse into one.
- Left/right modifier keys and Enter/numpad Enter share a key code, so they can't be bound separately.
- A repeated block error (e.g. a broken chat command) is logged every time it runs, not once.
